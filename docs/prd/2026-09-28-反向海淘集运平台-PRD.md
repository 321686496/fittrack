## 1. 项目背景与目标

### 1.1 行业背景（事实陈述，附来源）

反向海淘集运（Taobao Agent / 转运）是指：海外买家把淘宝、天猫、1688、微店（Weidian）、闲鱼等平台的商品链接交给平台，由平台**代买 → 收进国内仓 → 质检拍照 → 按买家指令合并打包 → 国际寄送**。

这个赛道在过去两年经历了剧烈洗牌：

- **Pandabuy 于 2024 年关停**，用户失去账号、库存与钱包余额存取权，数百万用户被迫迁移（来源：agentsben.com 对比文、repfindsarchive.com 评测）
- **WegoBuy 于 2025 年关停**（来源：taobao-spreadsheets.com 榜单）
- 市场从"4 家通吃"碎片化为 **30+ 家在运营**，榜单中同时标注"活跃"与"已关闭"两类状态

关键结论：**这个市场的淘汰不是被竞争对手打败，而是被合规风险击穿。** 因此本产品的合规能力不是加分项，是生存条件。

### 1.2 竞品定位对照（来源：repfindsarchive.com / taobao-spreadsheets.com）

| 竞品 | 服务费率 | 免费保管期 | 社区评价 |
|---|---|---|---|
| Superbuy | 约 5% | 180 天 | 系统成熟、客服响应好、**但偏贵** |
| CSSBuy | 4%~8% | 30 天 | **最便宜但 UX 最差**、旺季客服失联 |
| Sugargoo | 5% | 90 天 | QC 照片质量最好 |
| ACBuy | 约 5% | 90 天 | 综合体验最佳（北美主流） |
| CNFans | 0~3% | 60 天 | 费率最低、目录最大 |
| Mulebuy | 约 5% | 60 天 | 靠 EU IOSS 合规取胜 |
| Hoobuy | 0% | 60 天 | 社区驱动、巴西市场强 |

> 服务费率与保管期数字来自第三方评测站点，多为联盟营销性质，**不能直接作为定价依据**，仅用于理解竞争格局。

### 1.3 我们的产品定位

从对照表能看出两条未被同时满足的需求缝隙：

1. **"便宜"与"体验好"不可兼得**：CSSBuy 便宜但 UX 差、Superbuy 体验好但贵
2. **没有一家在多地区都做到税务合规**：Mulebuy 只解决了 EU IOSS，全球多地区合规是空白

**定位：面向全球多地区的、体验现代化且全链路合规的集运平台。**

刻意选择的三个支点：

- **体验支点**：PC 与 App 同源同体验，QC 照片高清可达（对标 Sugargoo 的强项）
- **合规支点**：以"严格合规"为产品红线，把合规能力做成可对外宣传的信任资产
- **多地区支点**：北美 / 欧洲 / 拉美 / 东南亚多币种多税制原生支持，不做地区特供版

### 1.4 商业目标与成功指标

| 目标层级 | 指标 | 说明 |
|---|---|---|
| 北极星 | 月度已完成包裹数（Delivered Parcels） | 直接反映"代购→出库→签收"全链路健康度 |
| 转化 | 链接提交 → 支付转化率 | 衡量解析准确率与定价可信度 |
| 留存 | 二次下单率（90 天内） | 集运是复购生意，一次性用户价值低 |
| 效率 | 入仓 → 上架时长、打包 → 出库时长 | 仓内作业效率，直接决定口碑 |
| 质量 | QC 照片 24h 内出图率 | 对标 Sugargoo 的核心竞争力指标 |
| 财务 | 毛利率（服务费 + 增值服务 + 运费差） | 需按订单与包裹双维度核算 |
| 风险 | 侵权申诉量、拒运率 | 合规红线的量化监控 |

### 2.2 内部角色（后台使用方）

| 角色 | 核心诉求 | 关键权限边界 |
|---|---|---|
| 采购员 | 快速接单、比价、下单、回填单号 | 仅采购域；不可改价、不可退款 |
| 收货员 | 扫码签收、快速录入 | 仅入库单 |
| 质检员 | 按清单拍照、判定、标记异常 | 可提交质检结论，不可改价 |
| 打包员 | 按包裹单拣货、复核、称重、出库 | 仅打包台 |
| 客服 | 全链路查询、工单、补偿 | 可发起补偿，需审批 |
| 财务 | 充值确认、对账、退款、理赔结算 | 财务域全权；不可改订单商品 |
| 风控审核 | 审核可疑商品、处理举报 | 风控域全权；可拦截订单 |
| 运营 | 公告、Banner、帮助中心、优惠券、活动 | 内容与营销域 |
| 超管 | 权限、字典、定时任务、渠道配置 | 系统域 |

> **权限设计原则**：后台所有金额相关的写操作**必须留痕且可分权**。"改价/退款/弃置/理赔"四类高风险操作一律走审批流，不允许单人闭环。

## 3. 业务全链路与核心流程

### 3.1 主链路（九步）

```
① 选品           用户在淘宝/1688/微店/社群看中商品，复制链接
② 提交           粘贴链接或上传图片 → 系统解析商品标题/图/SKU/价格
③ 代购下单       用户确认规格数量 → 生成代购订单 → 钱包扣款（或先充值）
④ 平台采购       采购员在源平台下单 → 回填商家快递单号
⑤ 国内入仓       仓库收货扫码签收 → 分配库位 → 状态通知用户
⑥ 质检拍照       质检员拍摄 QC 照片（外观/标签/尺码/瑕疵）→ 用户可查看
⑦ 合并打包       用户勾选在库商品 → 创建包裹 → 选增值服务 → 选物流线路
⑧ 支付运费       系统按线路报价 + 重量/体积重计费 → 支付 → 打包出库交运
⑨ 全程跟踪 → 签收 → 售后/理赔
```

### 3.2 关键分叉与异常流（必须覆盖，否则运营接不住）

| 异常 | 处理方式 |
|---|---|
| 商品下架 / 涨价 | 生成"采购异常"任务，用户可选：按新价补款 / 换货 / 取消退款 |
| 商家不发货 / 虚假发货 | 超时告警 → 采购员介入 → 可申请平台退款 |
| 缺件 / 少发 / 发错 | 质检阶段标记异常 → 生成索赔任务 |
| 商品破损到仓 | 质检标记 → 拍照留证 → 用户决定是否退货 |
| 包裹超保管期 | 到期前 N 天多渠道提醒 → 超期按天计费 → 长期未处理进弃置流程 |
| 扣关 / 退回 | 物流异常 → 客服介入 → 重新寄送或退运（产生费用需用户确认） |
| 包裹丢失 / 破损 | 走理赔流程，按保价与否分档赔付 |

## 4. 系统整体架构（四端）

本系统拆为 **4 个可独立交付的子系统**，共用一套领域后端：

| # | 子系统 | 用户 | 技术 |
|---|---|---|---|
| 1 | 用户端 PC Web | 海外买家、批量买家、代付人 | Vue3 + TS + Element Plus（SPA） |
| 2 | 用户端移动 App | 海外买家（主力场景） | Flutter（一套代码出 Android + iOS） |
| 3 | 运营管理后台 | 采购/仓储/客服/财务/风控/运营/超管 | RuoYi-Vue-Plus 二次开发 |
| 4 | 领域后端 + 数据库 | 上述三者共同依赖 | Spring Boot 3 + MySQL + Redis |

**架构形态（已确认）：模块化单体 + 3 个边缘异步服务**

```
                    ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
                    │ 用户端 PC Web │  │  移动 App    │  │  运营后台    │
                    │  Vue3 SPA    │  │  Flutter     │  │  RuoYi       │
                    └──────┬───────┘  └──────┬───────┘  └──────┬───────┘
                           │                 │                 │
                           └────────┬────────┴────────┬────────┘
                                    ▼                 ▼
                        ┌─────────────────────────────────────────┐
                        │      API 网关 / BFF（鉴权·限流·幂等）      │
                        └───────────────────┬─────────────────────┘
                                            ▼
        ┌───────────────────────────────────────────────────────────────────┐
        │                  核心应用：模块化单体（Spring Boot 3）              │
        │  order │ purchase │ wms │ logistics │ finance │ iam │ risk │ cms   │
        └───────┬───────────────────────────────────────────────┬───────────┘
                │                                               │
                ▼                                               ▼
        ┌───────────────┐   ┌────────────────────────────────────────────────┐
        │ MySQL（主库）  │   │      边缘异步服务（可独立扩缩容）                │
        │ Redis（缓存）  │   │  ① 链接解析与图片抓取（代理池/限流）             │
        └───────────────┘   │  ② 报表与结算批处理                             │
                            │  ③ 消息推送（Push / 邮件 / 短信）               │
                            └────────────────────────────────────────────────┘
```

**为什么这三块必须独立**：它们都**不需要事务一致性**，且负载特征与在线交易完全不同——链接解析易被源平台风控（需代理池与退避）、报表跑批重 IO、推送需重试与去重。放在单体里会互相拖累。

**为什么不一开始就微服务**：集运业务的强一致场景极多（下单即扣钱包、入仓改库存、打包出库、结算对账），分布式事务与对账复杂度是**指数级上升**，而初期团队规模不足以摊薄这个成本。

## 6. 关键状态机

状态机是本系统的骨架，任何状态跳跃都必须走显式流转并留痕。

### 6.1 代购订单（Agent Order）

```
待支付 → 已支付 → 采购中 → 已采购 → 国内运输中 → 已入仓 → 质检完成 → 已完成
   │        │        │         │                        │
   │        │        └─────────┴──→ 异常处理中 ──→ （补款/换货/取消退款）
   │        │
   └────────┴──→ 已取消 / 退款中 → 已退款
```

| 状态 | 允许操作 |
|---|---|
| 待支付 | 支付、取消 |
| 已支付 | 取消（需审批） |
| 采购中 | 取消（需与采购员确认） |
| 已采购 | 不可取消，可申请退货 |
| 国内运输中 | 不可取消 |
| 已入仓 | 可申请退货、可合并 |
| 质检完成 | 可合并、可申请增值服务 |
| 异常处理中 | 补款 / 换货 / 取消退款（三选一） |
| 已完成 | 仅售后 |

### 6.2 在库商品实例（Warehouse Item）

```
待到货 → 已签收 → 已上架 → 质检中 → 质检完成 → 已锁定(被包裹占用) → 拣货中 → 已出库
                                  │            │
                                  ├→ 异常待处理  └→ 已释放(取消合并)
                                  └→ 已退回商家 / 已弃置
   任意在库态 → 超期(计费中)
```

### 6.3 包裹（Parcel）

```
草稿 → 待支付运费 → 已支付 → 拣货中 → 打包中 → 已打包 → 已出库 → 已交运
                                                                    │
        ┌───────────────────────────────────────────────────────────┘
        ▼
   运输中 → 清关中 → 派送中 → 已签收
        └→ 异常（扣关/滞留/退回/丢失）→ 客服介入 → 重寄 / 理赔
   出库前任意态 → 已取消
```

### 6.4 其他

| 对象 | 状态 |
|---|---|
| 采购任务 | 待领取 → 已领取 → 下单中 → 已下单 → 已完成 / 异常 |
| 充值订单 | 待支付 → 支付中 → 成功 / 失败 / 已关闭 |
| 工单 | 待受理 → 处理中 → 待用户确认 → 已解决 → 已关闭 / 已升级 |
| 理赔 | 已申请 → 审核中 → 已通过待赔付 → 已赔付 / 已驳回 |
| 风控审核 | 待审核 → 已通过 / 已拒绝 / 待补充 |

| **Logistics 物流域** | `carrier`、`shipping_line`、`rate_card`、`rate_card_version`、`parcel`、`parcel_item`、`packing_record`、`parcel_tracking`、`customs_declaration`、`shipping_label` |
| **Finance 财务域** | `wallet`、`wallet_transaction`、`recharge_order`、`payment_channel`、`refund_order`、`bill`、`reconciliation`、`claim`、`coupon`、`coupon_usage`、`exchange_rate` |
| **Risk 风控域** | `brand_blacklist`、`keyword_rule`、`risk_hit_record`、`review_task`、`report_record` |
| **CMS/System** | `announcement`、`banner`、`help_article`、`category`、`ticket`、`ticket_message`、`notification`、`i18n_text`、`sys_*`（RuoYi 原生） |

**建模要点**

1. `warehouse_item` 是**实物实例**而非 SKU——每个入库实物唯一编码，可追溯全生命周期
2. `parcel` 与 `warehouse_item` 是**多对多**（`parcel_item`），支持合并与拆包
3. `product_snapshot` 保存下单时刻的商品信息快照，避免源平台改价改图导致历史订单不可解释
4. 所有金额字段存**最小货币单位整数**（如分），禁止浮点
5. 所有核心表带 `region` 预留字段，为多地区扩展留口
6. `rate_card` 必须版本化，历史包裹按当时报价核算，不允许被新报价篡改

## 9. 合规与风控专章

因为选定了**严格合规**路线，本章是产品的生存条款，而非附属说明。

### 9.1 硬性红线（产品级禁止）

1. **禁止**任何形式的品牌侵权、仿牌、假冒商品代购与运输
2. **禁止**明知侵权仍协助规避申报
3. **禁止**运输各国明令禁止的品类（毒品、武器、活体、违禁药品等）
4. **禁止**协助虚假申报（低报价值、错报品名）以逃避关税

### 9.2 产品化落地手段

| 手段 | 落点 |
|---|---|
| 品牌与关键词黑名单 | 提交链接时实时拦截，命中即拒绝或转人工审核（A-RISK-01/02） |
| 图片风险比对 | 以图搜货与商品图上传路径接入（A-RISK-03） |
| 人工审核队列 | 所有命中规则的商品必须人工过审（A-RISK-04） |
| 目的国差异化限制 | 同一商品发不同国家可售性不同，按线路配置禁运品类（A-RISK-05） |
| 举报通道 | 对外公开举报入口 + 内部处理闭环，对标 Superbuy 的 report-counterfeits 机制（A-RISK-06） |
| 用户协议与免责 | 注册与下单环节明示禁运范围与责任划分 |
| 留存与举证 | 审核结论、质检照片、申报记录全程留证，应对纠纷与监管 |

### 9.3 行业警示（为什么必须这么做）

Pandabuy 2024 年关停、WegoBuy 2025 年关停，直接原因与法律压力及侵权商品运输高度相关，用户库存与钱包余额随平台一同冻结。**这条路径上，"业务增长"与"平台存活"是同一个命题。**

## 10. 技术架构与选型（已确认）

| 层 | 选型 | 理由 |
|---|---|---|
| 用户端 PC | Vue3 + TypeScript + Element Plus（SPA） | 行业获客靠社群/表格，**无 SEO 刚需**，不需要 SSR |
| 用户端 App | Flutter | 一套代码出 Android + iOS；与团队既有 Flutter 积累延续 |
| 运营后台 | RuoYi-Vue-Plus 二次开发 | 权限/菜单/字典/日志/代码生成省掉一半地基工作量 |
| 后端 | Spring Boot 3 + MyBatis-Plus | 团队主栈；模块化单体按域分包 |
| 数据库 | MySQL 8（主库）+ Redis | 事务能力满足集运强一致场景 |
| 文件存储 | 对象存储 + CDN | QC 高清图、面单、凭证 |
| 消息队列 | Redis Stream / RabbitMQ | 异步任务、推送重试、去重 |
| 边缘服务 | ①链接解析与图片抓取 ②报表与结算批处理 ③消息推送 | 均为无事务一致性要求的高负载/高不确定性任务 |
| 可观测 | 日志聚合 + 链路追踪 + 指标监控 | 全链路 Trace ID 贯穿 |

**明确不做（YAGNI）**

- 不做微服务拆分（初期团队规模摊不平分布式事务与运维成本）
- 不自建支付收银台（规避 PCI-DSS）
- 不做服务端渲染（无 SEO 需求）
- 不做多租户 SaaS（当前是自营平台，非 SaaS 产品）

## 11. 里程碑与交付阶段

> 以下按**依赖顺序与验收标准**定义，不涉及时间估算。

### M1 — 跑通最小闭环（可真实接单）

**范围**：领域后端骨架 + 运营后台（订单/采购/入库）+ 用户端 PC 最小下单链路

**验收标准**：
1. 用户可注册、充值（至少一种支付通道）、粘贴链接下单、查看订单状态
2. 采购员可在后台领取采购任务、回填快递单号
3. 收货员可扫码签收，商品进入在库状态
4. 全链路状态变更对用户端可见
5. **一笔真实订单可从下单走到入仓，无人工改库操作**

### M2 — 完整仓配与结算

**范围**：完整 WMS + 物流渠道与报价 + 财务钱包与运费支付 + 风控审核（基础版）

**验收标准**：
1. 库位管理、质检拍照、保管期计费、库存锁定全部可用
2. 报价表可 Excel 导入，运费试算与实算一致
3. 用户可合并商品、选线路、支付运费，仓库可打包出库交运
4. 财务可对账，毛利可按订单维度核算
5. 品牌黑名单命中可拦截并进入人工审核

### M3 — 移动 App

**范围**：Flutter 双端 App（能力对齐 PC）+ 推送 + 扫码拍照

**验收标准**：
1. App 可完成 PC 端全部核心流程
2. 订单与包裹状态变更可实时推送
3. 支持以图搜货与理赔凭证上传
4. iOS 上架要求满足（Apple 登录、隐私清单）

### M4 — 营销与多地区完善

**范围**：优惠券/会员/邀请返利 + 多语言多币种完善 + 风控规则引擎化 + 报表中心

**验收标准**：
1. 多语言文案可后台维护，切换即时生效
2. 多币种展示与结算贯通，汇率可控
3. 营销工具可独立配置并核销
4. 风控规则可配置不依赖发版

## 12. 风险与依赖

| 风险 | 影响 | 应对 |
|---|---|---|
| **合规风险（最高）** | 平台关停，用户资产冻结 | 严格合规红线 + 风控模块前置到 M2 而非最后 |
| 链接解析被源平台风控 | 核心转化路径失效 | 独立服务 + 代理池 + 手动提交兜底（U-ORD-04 必须 P0） |
| 支付通道开户与风控审核 | 收款能力受限 | 多通道并行接入，避免单点 |
| 物流货代对接与报价准确 | 运费算错直接亏损 | 报价表版本化 + 试算与实算强校验 + 人工复核 |
| 高价值商品纠纷（丢件/破损） | 赔付成本与口碑 | 保价机制 + 质检留证 + 理赔标准前置公示 |
| 多地区税务政策变动 | 合规失效 | 税务规则配置化，不硬编码 |
| QC 照片量级带来的存储成本 | 成本不可控 | 分级存储 + CDN + 生命周期策略 |

**外部依赖**

- PayPal / Stripe / Wise 商户账号（需企业主体与资质）
- 至少 1 家货代 API 对接文档与账号
- 支付与物流的合规资质评估（含数据出境）

**待确认事项（进入实施前必须闭环）**

1. 公司主体与收款主体所在地区（决定支付开户与税务方案）
2. 首批目标国家优先级排序（决定物流线路与语言排序）
3. 免费保管期的具体天数与超期费率（决定 U-WMS-03 / A-WMS-08 参数）
4. ~~服务费费率口径~~ **已确认**：采用**统一费率 + 档位可配**（默认约 5%）。
   - 费率不硬编码，后台维护**费率档位表**，支持按品类 / 物流线路 / 会员等级配置不同档位
   - 用户端价格展示与后台结算均从同一档位表取值，保证"预估 = 实算"
   - 仍未定：**最低收费金额**（小额外单的兜底规则），不影响开发启动
5. 仓库所在城市与规模（决定 WMS 库位模型与硬件选型）
